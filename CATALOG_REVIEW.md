# Catalog review with the owner

This is WAI's catalog review process as of October 19, 2026. The dictated review protocol and initial-v1 scoring rubric are its operating standards. Apply them to new reviews and substantive reassessments. A method change must be dated, explained, and applied prospectively; it does not silently rewrite saved or public scores. The owner remains the final editorial approver. A bounded, qualified review is complete when the main product relationship, supported claims, material limitations, scores, and evidence scope are clear, even if optional features remain untested.

The public finder is account-free. This review process is editorial, not a visitor sign-in feature. The original 36 entries are explicitly marked `Legacy public` in the admin dashboard and remain available while their owner review is pending. Their current `Researching` and `Evaluation ready` labels must not be interpreted as owner approval. This is a visibility exception for the existing catalog, not a shortcut for new submissions.

## One card per proposed entry

Present each proposed new entry or substantial profile revision to the owner in chat as a short, mobile-readable card with an ID such as `WAI-hevy-20260929-r1`. Do not ask the owner to inspect `lib/catalog.ts` or a database record. Keep the card factual, with direct links to the app's own site, its current store listings, and any other source actually used. Show the date each time-sensitive fact was checked.

Use this order:

1. **App and proposed position:** name, product category, best fit, and the user who probably should not choose it.
2. **What it does:** programming model, decisions the app removes, decisions the user still owns, and the main convenience-versus-control tradeoff.
3. **Practical facts:** supported platforms, current price/trial/free-tier limits, AI role, equipment or training setting, and standout features.
4. **Differentiation and caveats:** what is genuinely distinctive, what is ordinary, and meaningful limitations. Show score recommendations with a short rationale, not just numbers.
5. **Evidence and uncertainty:** source links beside the claims they support, check dates, and explicit unknowns or conflicts. Do not convert an unknown into a confident score or eligibility claim.
6. **Proposed public summary:** the concise wording visitors would see.
7. **Decision:** discuss changes here; for an existing saved entry, the owner accepts proposed fields in admin and separately confirms the exact record as Reviewed. A partial chat reply is feedback, not publication approval.

Keep the default card brief enough to review on a phone. Offer additional evidence or detail only when useful. If a source does not support a claim, revise the claim before presenting the card. A developer submission is a lead, not independent evidence.

For routine app evaluation, use `CATALOG_DICTATED_REVIEW_PROTOCOL.md`. The owner dictates observations in chat; WAI tracks the same product checkpoints in the background, asks only targeted follow-ups, reconciles them with dated source claims, and applies `CATALOG_SCORING_RUBRIC.md`. A normal review budgets about 60-90 minutes of hands-on use across one principal journey, one reasonable retry, and one obvious alternative route. Do not send the owner a form to fill out or require extra workouts merely to complete a checklist.

## Local research to admin approval

Research, scoring, proposed copy, and dated source records are prepared in the local project with the owner. A new Candidate can be prefilled from a local research draft, but a saved Firebase record is never overwritten by a later code deployment. When a local draft differs from an existing saved record, the admin editor shows each changed field as **Saved now** versus **Proposed**. The owner accepts only the fields they choose; all other saved fields, including their own edits, remain unchanged. A stale comparison is rejected if the saved record or local proposal changed after the page opened. Score totals are recalculated only when an accepted criterion changes. Saving a private card or accepting a proposed change attaches any new, explicitly prepared source records without replacing owner-edited evidence. This does not change review status or publish the app.

Applying selected fields changes the private catalog record and attaches only missing prepared source records. It does not mark the app Reviewed, publish a listing, or trigger a site deployment. After acceptance, the owner reviews the full card and source log, confirms Reviewed when ready, and uses the separate **Publish approved catalog** control for public changes. Submission tracking remains in the admin inbox. More hands-on testing is optional unless a specific public claim cannot be supported or responsibly qualified without it.

### Handoff from an individual app review chat

Use this sequence for each app. An app-specific `RESEARCH_*.md` is the private working evidence and reasoning record, **not** the admin card and not a file the site imports. The admin-facing proposal is the matching `AppRecord` in `lib/catalog-research-drafts.ts`; dated, claim-specific sources for the admin Source log go in `lib/catalog-prepared-evidence.ts`. The saved private card lives in Firestore. A public listing is a separately published snapshot. Keep these four things distinct in chat and in status reports.

1. **Prepare the local proposal.** Reconcile the app-specific research notes, current public sources, owner testing, scoring rubric, and proposed consumer copy. Update the app's `AppRecord` and prepared evidence with the same stable app ID. Check score arithmetic, dates, source attribution, unresolved claims, pricing and finder flags. Do not put raw testing chronology into public-copy fields. A developer submission is a lead, not a source. Show the owner material score or conclusion changes and their evidence before treating them as approved.
2. **Validate and hand off the exact files.** Run the relevant catalog tests, lint, and production build. Review the diff and list every intended changed or new file by name, including the `RESEARCH_*.md` file, both `lib/catalog-*.ts` files when changed, and any tests. Distinguish unrelated working-tree files. A local edit does not reach the admin site until those exact files are committed and a successful site rollout includes them. Do not imply that updating the Markdown file alone updates the card. Do not commit or deploy merely because a draft is ready unless the owner has authorized that step.
3. **Open the admin card after rollout.** The owner checks `/admin/apps/<app-id>` and compares **Saved now** with **Proposed** under **Local research update**. For a new local-only draft with no saved Firestore card, the editor can show the proposal but the review checklist is not yet satisfied; use **Save catalog record** once to create the private card. For an existing saved Candidate/Researching/Evaluation ready card, choose the proposed fields to accept and click **Apply selected changes to private record**. The complete-draft action is only for an explicit review of every difference. The apply action saves immediately; do not also click **Save catalog record** unless making further manual edits. Unselected saved fields and owner edits remain intact. A stale-comparison message means reload and compare again; never force an older proposal over newer saved work.
4. **Check the persisted result, then approve separately.** Reopen or refresh the card. Confirm the accepted wording, criterion scores, calculated totals, practical facts, and dated Source log in the **saved** card; the editor may display an unsaved local proposal over a Candidate placeholder. The **Saved card review checklist** evaluates Firestore, not the displayed proposal or the number of features tested. If research or evidence is missing, return to the app review chat for a local correction and another rollout. Changing **Review stage** never saves research fields. Once the exact saved card is complete, the owner checks its sources, selects **Reviewed**, confirms that exact version, and updates the stage. Do not interpret **Evaluation ready**, a passed research check, or an agent's completed draft as owner approval.
5. **Publish only when intended.** **Reviewed** is still private for a new submission. The owner uses **Publish approved catalog** separately, confirms its success message and version, and verifies the public browse card and profile. Publishing uses the saved Reviewed record, not the current local files, and does not require another code rollout if the site already contains the proposal UI and the owner has only accepted saved-field changes. The original 36 legacy-public entries are the documented visibility exception.

For later updates to a **Reviewed** card, the local comparison is informational and cannot be applied while it remains Reviewed. The owner must decide to reopen the card as **Researching**, compare the newer local proposal against the saved version, accept selected changes, and complete the review and publication gates again. Do not reopen or republish a card automatically. If the owner edits the admin card directly, preserve those saved edits in later local work; the local draft is a proposal, never the authority over a saved record. At handoff, report three statuses separately: local proposal prepared, private card saved/reviewed, and public snapshot published/verified.

## Approval gate

- Research and drafting may set an entry to `Candidate`, `Researching`, or `Evaluation ready`. They never set it to `Reviewed` merely because an agent checked sources or filled every field.
- Set `Reviewed` only after the owner has seen the saved admin card and explicitly approved that version of the entry. Apply requested edits before marking Reviewed.
- A substantial later change to pricing, AI role, programming model, fit, scoring, or claims needs a new card and approval. Routine typo fixes do not.
- For newly researched apps, proposed scores belong on the private card before owner approval. Use the same documented criteria for each app, distinguish store/developer claims from hands-on observations, show category scores and rationale, and mark evidence-limited scores as provisional. Developer answers may correct facts but do not set WAI scores. See `CATALOG_SCORING_RUBRIC.md` for the initial-v1 rubric applied to the first two submitted-app drafts.
- The original 36 have private, evidence-limited Legit and Originality rescoring drafts documented in `LEGACY_RESCORING.md`. Their public scores remain unchanged until each exact revision is approved and published. The admin editor will not overlay a draft onto an owner-edited score or an already Reviewed record.
- Do not automatically publish or deploy a card on approval. Verify the approved facts and the site build, then use the normal release process.
- Do not take down the existing public catalog merely because a newer Firebase publication has not yet been created. The fixed 36-ID legacy-public set is the documented baseline, including after later publications. Adding a new app to the bundled source does not make it legacy public.
- Each publication overlays the latest approved versions onto that legacy baseline and adds approved new entries. Unreviewed new Candidates and research drafts are never included in public listings or the sitemap.

The private Firebase catalog manager is the owner's approval and publication surface. Its `Reviewed` status and publish controls remain separate from accepting local research changes field by field.

Developer participation is not required before publication. WAI does not send routine research-stage updates, negotiate scores in advance, or offer prepublication approval. Developers can submit documented factual corrections and material product updates through the site's correction channel. A factual clarification can be requested when necessary, but no response is not itself a support failure or a publication veto. Normal customer-facing support may be evaluated if encountered; editorial correspondence with WAI does not earn Support/privacy points. Verified product changes may affect the applicable product criterion after WAI checks the updated behavior.

Keep routine catalog research and observations in the local project. A separate Google Doc may be used for a paid private audit deliverable, but catalog updates do not require maintaining a parallel document. Do not copy raw test notes wholesale into a public listing, and do not turn an observation into a confirmed defect without verification.

## Developer submission intake

- `Mark seen` only acknowledges that the owner has looked at an inbox request. It does not create a catalog entry or approve any claims.
- `Accept for research` links the submission to an existing evaluation with the same app name or creates an unpublished `Candidate` with explicit unverified placeholders. Keep the original submission in the inbox as a lead, not as independent evidence.
- A code-supplied research draft may appear in the admin list before a Firebase record exists. It is private and must be saved in the editor to persist changes. Accepting its matching submission later links the lead to that evaluation; it does not approve or publish the draft.
- Research and edit the Candidate separately. Only the approval gate above can move its catalog record to `Reviewed`, and publication remains a separate action.

### Capacity-controlled queue

- App submissions are internally classified as unverified research leads. The public receipt says only, "We received your submission," and does not promise testing, review, listing, publication, or a timeline.
- Initial screening and acceptance for research have no monthly quota. The dashboard still counts them by UTC month. A screen should take no more than 10 to 15 minutes. Several apps may be in research preparation or carry the admin `active_review` stage, but schedule hands-on testing for only one app at a time. This is an editorial operating limit, not a software-enforced cap or a limit on preparing private cards.
- Status path: `received` → `screening` → `waitlisted_eligible` → `accepted_for_research` → `active_review` → `research_ready`. Existing `waitlisted_unassessed` submissions can enter screening; no new submissions are placed there because of a quota. `not_scheduled` and `declined` are explicit owner dispositions. Only the owner can move stages in the admin dashboard. Existing `new`, `seen`, and `accepted` submissions are mapped to their closest new state without publishing them.
- Check a live public product, substantive fitness training or tracking, a working website or store listing, a public privacy policy, stated platforms/pricing, and practical review access. Record a brief note. Passing checks means eligible for consideration, not independently verified for the catalog.
- `Mark seen` is a timestamp and does not move the app through editorial stages. `Accept for research` still only creates or links an unpublished Candidate. `Research ready` means an owner-review card is ready; it is not catalog `Reviewed` or published.
- The dashboard pages submissions 30 at a time. New submissions are visible at the top; use the older-submissions link for the rest. Later developer messages remain personal. The existing new-submission notification goes only to the owner. No submission fee or payment workflow is implemented.
- The separate $250–$350 private positioning audit is optional commercial work. Payment must never affect editorial selection, WAI scoring, ranking, conclusions, or publication.

### Analytics decision and release check

- GA4 automatic page views are authoritative for real URLs. The Google tag `config` sends the initial page view; GA4 Enhanced Measurement sends history-change page views. The old manual `page_view` on home-screen tab changes was removed because those tabs do not change URLs and could inflate Views. The live WAI Views card showed synthetic titles such as `Workout App Index - finder` and `Workout App Index - browse`, confirming those manual events reached reports. Do not add another manual page-view call without disabling the automatic source first.
- Live GA4 audit on 2026-10-08: in the **Workout App Index** property, the data-flowing stream uses measurement ID `G-VQ7RCBS9H6`. Enhanced Measurement is on; Page loads and browser-history page changes are checked. **Outbound clicks** and **Form interactions** are also on. The older `Workout App Index Web` stream uses `G-TZNQ4MN555` and is distinct; do not change the wrong stream.
- Before release, in GA4 → Admin → Data streams → **Workout App Index** → Enhanced measurement → gear, leave Page views and browser-history page changes on, but disable **Outbound clicks** and **Form interactions** in the data-flowing stream, then Save. Outbound `click` includes full `link_url`; auto `form_submit` records the click before the server confirms a save, so neither matches WAI's custom-event policy. This live GA4 setting was audited but not changed while the code awaits review. The older stream can be cleaned up separately after confirming no tag sends to it.
- `submission_started` fires once per app form mount on the first nonempty user input, with no parameters. `submission_completed` fires only after the server returns HTTP 201 with `ok: true` following the Firestore save. Failed requests and correction forms do not emit these events. The honeypot path does not return success.
- `outbound_app_click` fires from profile action buttons only. Its exact parameters are `destination_type` (`store` or `official_site`), `placement` (`profile`), and the public `app_slug`. It excludes URLs, submission IDs, developer IDs, and form content. The buttons are intentionally not ordinary outbound anchor links so Enhanced Measurement does not automatically attach a full URL if its stream setting has not yet been corrected.
- All custom events require granted analytics consent. In GA4 DebugView or a test property, check one form start per form session, completion only after a successful save, one outbound event per click, and one page view per real page navigation. Compare before and after Views rather than combining periods with the old manual behavior.
